The prepared manifest requests RenderBackend0, but configuration intent and a process observation remain separate facts.

Microsoft documents that Direct3D initialization changes its calling thread to single precision and nearest rounding unless D3DCREATE_FPU_PRESERVE is used. This is primary support for the causal hypothesis linking source CreateDevice to the observed main-thread candidate CW 0x007f; it is not proof that this captured process took that precise call path or never changed control afterward. See [Microsoft Windows-title FP control guidance](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/top-issues-for-windows-titles) and [archived IDirect3D8::CreateDevice contract](https://learn.microsoft.com/en-us/previous-versions/ms889264(v=msdn.10)). The latter explicitly places FPU state under the Direct3D8 preservation policy. [D3DCREATE reference](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dcreate) independently describes the same default, but is a Direct3D9 reference rather than a byte-level proof of the loaded Direct3D8 DLL.

The resulting source model is a per-thread transition: actual CRT initialization selects53-bit; Direct3D creation can then select24-bit in its caller; later callees may temporarily alter and restore that caller's state. The different thread CW values fit this model, but do not prove the cause of every worker's53-bit setting or a constant gameplay CW.
