# Review, 2026-10-16: five days of agent work, and why the screen stopped changing

Written after the user reported two things: the latest round showed only the SEGA screen,
where earlier rounds had shown the Sonic title screen; and the code is still hard to read
(the example was `ninja_fog_generate_table_787260` in `src/engine/ninja_fog.cpp`). The
decisions that follow from this review are in
[ADR-0008](decisions/ADR-0008-visible-journeys-and-proportionate-verification.md) and in
`docs/GOAL.md` (rewritten the same day). The previous review is
[REVIEW-2026-10-12](REVIEW-2026-10-12.md).

## 2. Why the user saw only the SEGA screen

Measured on 2026-10-16 with `build/sadx-app --guest reference/updated-pc-reference/game
reference/windows-system`:

* The gate's `app-smoke` runs **120 frames** and checks for the "PRESENTED BY SEGA" screen,
  then closes the window. During a gate, that is all the user ever sees.
* Run by hand without input, the SEGA logo lasts until frame 387. The intro movie then plays
  headless: it is **not drawn** (one clear per frame, a black window), and the app advanced
  at about **6 frames per second** in this measurement (other work was running on the Mac;
  the headless gate run is faster). The title appears near frame 7,900, which is roughly 20
  minutes of black screen.
* With Enter at frame 450 (`--keys 450:13`), the title screen appears and is correct by
  frame 700, **24 seconds** after launch.
* With Enter presses through the menus, the app reaches file select and **character
  select** (a 100 % save is in `reference/updated-pc-reference/game/savedata`). Choosing
  Sonic loads the 3D world at frame ~1,892. From then on the window is a **solid cyan
  clear**: every 3D draw is skipped as `not drawn: FVF 322` (decimal; `0x142` = XYZ |
  DIFFUSE | TEX1). `src/platform/mac/metal_guest_frame.mm:90` draws only pre-transformed
  (XYZRHW) vertices. The guest does not stop, so the game runs underneath an empty screen.

* With the harness added the same day (`tools/journey/sadx_driver.py`), the game reaches
  Station Square by frame ~1,950: game mode 5, stage 26, act 3, game state 15, Sonic present.
  Holding the left stick forward for 120 frames moved Sonic from (62.7, 0, 1454.3) to
  (12.5, 26, 1352.5), at speed 0.9 and action 2. **The game is already playable inside the
  reference runtime. Only the 3D drawing is missing.**

So nothing regressed. The previous title-screen views came from runs where an agent pressed
Enter. Every round since has shown the same 120-frame smoke window, and no session since 10-13
ran the app past 120 frames or looked at a screen. The wall between "menus" and "gameplay" is
a Metal **fixed-function 3D renderer** (world/view/projection transforms, lighting, materials,
fog, texture stages, vertex and index buffers). Nobody has worked on it.

## 3. Where the effort went on 10-16

From the Codex session logs (`~/.codex/sessions/2026/10/16`) and `git log --numstat`:

* One `/goal` thread ran 24.7 hours of wall time (11.8 active): 1,167 shell commands, about
  22 full gates (all rc 0), 241 oracle commands, 39 commits, 5 context compactions, and 268M
  input tokens (mostly cached). It was never stuck and never failed a gate.
* The eleven initialization steps (gates 151–162) moved between 7 and 1,869 constants each.
  Each took 17–36 minutes; the render-queue step took 102 minutes, including a 77-minute
  stall. A median of about 13 % of each step's time went into writing source, and about 45 %
  into verification, judges and evidence.
* Lines added in that series: game-tier source 1.7 %, reference adapters 3.5 %, judge and
  evidence files about 92 %. Each step's judge commit added a gate JSON of about 1,200 lines
  plus 15–20 harness and evidence files under `reference/production-integration-20261016/`.
  The repository now holds about 170,000 lines of gate evidence against 35,000 lines of `src`.
* Per step, the agent re-read HANDOFF about 4 times, GOAL 3.5, STYLE 2.5. The mandatory
  reading list was about 3,100 lines, roughly 50,000 tokens, before writing any code.
* Every step ran an independent reviewer subagent with three review rounds, and wrote its own
  constructor, bridge, CLI and mutant harnesses from scratch.

The docs caused the pattern:

* "Do exactly ONE step"; "one function, tight cluster or module per step".
* Every step required an oracle, mutants, a holdout set, an independent review, a full gate
  and a second `fix(judge)` commit. The judge manifest hashes the Makefile and the test
  manifest, so any new test forces that second commit and a second gate.
* GOAL §6 item 7 was a running list of families with no exit criterion. It ended with "these
  families do not complete the runtime refactor", which invites one more family.

## 4. Readability: what improved and what did not

Improved, and a good model for future code:

* `src/game/game_mode.cpp`: a named `GameMode` enum, structured flow and named seams.
* `src/player/ground_acceleration.cpp`: named tuning values and named steps, though cluttered
  by `ExactFloat` wrappers on every operand.
* The `*_initial_state` files are plain data with literals.

Not improved:

* The ratchet totals (hex 11,628, `_at_` 1,796, address calls 75, long lines 1,489,
  multi-statement lines 2,184) did not move from gate 151 to 162. Most of the earlier drop
  (hex 13,465 → 11,628; address calls 249 → 75; `goto` 73 → 2) came from **moving** legacy
  files into `src/guest`, which the ratchet exempts. They were not rewritten.
  `src/guest/native_game_reference.cpp` (1,652 lines) is now the largest file of game
  behaviour, and it is address-shaped.
* 7,044 of the 11,628 counted hex literals sit in two generated tables
  (`sonic_animation_operations.hpp`, `sonic_animation_table_data.hpp`), so the headline
  number is mostly noise.
* Emulator-style x87 code (`op.at(0x…)`, `fp.multiply_float_memory`, `X87Context`) remains
  in 41 of 47 `src/player` sources and 8 of 28 `src/engine` sources. `ninja_fog.cpp`, the
  user's example, has 66 `op.at(0x…)` markers.

The root cause of the last point is a judge problem, not a style problem. STYLE §7 allowed
plain `float` only where the FPU census shows `0x007f` (24-bit). The census, run in the guest,
shows `0x023f` (53-bit) everywhere. The guest's Direct3D 8 `CreateDevice`
(`src/hle/hle_d3d8.cpp`) does not do what the real one does. Without
`D3DCREATE_FPU_PRESERVE`, which SADX does not pass, Direct3D switches the calling thread to
single precision and round-to-nearest. The user's own Windows capture saw the earliest (main)
thread at `0x007f`. Under 24-bit precision, x87 `float` arithmetic matches plain IEEE `float`
except for a few named cases: `double` constants, float-to-int conversion, transcendentals,
and exponent-range extremes. Those are what the `sadx::fidelity` helpers are for. Fixing the
reference therefore unlocks readable physics, and it probably matters for M4 trace parity too.

* About 3,100 lines of mandatory reading per step, and the list grows. Each initialization step
  appended a paragraph to ARCHITECTURE, to GOAL §6.7 and to TIPS.
* Stale statements:
  * AGENTS.md allowed new `_at_` owners "until" `check_provenance.py` is in the gate. It is
    in the gate.
  * AGENTS, STYLE and ADR-0007 described `check_readability.py` as future work. It runs in
    the gate.
  * GOAL item 3 is done but was still written as open.
  * Readability baselines disagreed between GOAL, ROADMAP, ADR-0007 and STATUS.
  * ROADMAP and METHOD pointed to a "GOAL §4.5" that does not exist.
  * `NEXT-AGENT-PROMPT.md` (stuck at gate 129) and `AGENT_GUIDE_v1.md` (which still teaches
    `_at_<hex>` members and Hopper) were still linked as working documents.
* No document defined a visible milestone for the app beyond the 120-frame SEGA check.

## 6. What changes

See ADR-0008 and the rewritten `docs/GOAL.md`. In short:

1. **The visible journey ladder is the spine of the plan.**
   * Reference app: title → menus → 3D world drawn → Sonic playable in Emerald Coast with a
     replay.
   * Native app: SEGA logo → title → menus → stage → Sonic, without `sonic.exe`.
   * Each rung is an automated frame check plus a `make` target the user can run.
2. **Fix the guest's Direct3D FPU behaviour.**
   * Re-baseline the guest digests once.
   * Rerun the census.
   * Then rewrite the x87-style modules as plain `float` under their unchanged oracles.
3. **Make verification proportionate.**
   * One gate per step.
   * New tests are committed with their code.
   * Only edits to existing judges get a separate commit.
   * No throwaway harnesses are committed.
   * Short HANDOFF entries.
4. **Give steps a floor size.**
   * A step is a whole system, a whole module rewrite or a journey row.
   * The remaining initialization families are batched into one step with an exit criterion.
5. **Cut the per-step reading to four documents** and move the stale guides to
   `docs/history/`.
