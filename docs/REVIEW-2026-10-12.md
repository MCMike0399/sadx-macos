## The rate, honestly

`sonic.exe` `.text` is 4,038,656 bytes with ~9,268 distinct direct call targets.
The 89 oracle reports pin 98 verified code ranges totalling **6,022 bytes (0.15 %)**
covering 92 call targets. The gates from `render` (2026-10-11 20:14) to `endscene-98`
(2026-10-12 19:47) span one day. The user's estimate of a late-2027 playable build was,
if anything, generous: the measured rate is ~3 KB/day of verified code and the game
needs most of its code to be playable.

The limiting factor is not REA, Hopper or Ghidra. It is the method: exact per-function
re-implementation with a per-function emulator oracle is the *most expensive possible*
way to get behaviour, and it was applied to every function in boot order, including
cold paths (CD-drive scans, registry reads, message pumps). It is the right tool for
hot paths that must be bit-exact (player physics) and for the platform boundary; it is
the wrong tool for 9,000 functions of game logic.

## What is worth keeping (all of it, differently used)

1. **The verification toolchain** — PE image reader, Unicorn oracle harness, mutation
   testing, gate records with source hashes, owner and profile-patch checkers. This is
   the core asset. In the hybrid plan the same harness verifies native overrides
   against the in-process guest.
2. **The exact arithmetic models** (`src/cpu`): x87 ext80 context with control-word
   semantics, SSE with MXCSR, Bochs transcendental tables, CRT math. These shim the
   places where QEMU is not Intel-exact.
3. **The ported modules** as native overrides. Player physics, collision, animation
   and the render queue are the hot paths; they are already exact.
4. **The profile knowledge**: `tools/gate/profile_patches.json` (618 loader/mod patches,
   profile-evaluated) and the handoff's per-function notes.
5. **The boot composition** (`game_runtime`): it documents the exact boot order and
   every assumption; it becomes the reference for what the guest must reproduce.

## What was weak

* **Flat structure**: 243 source files, 208 test files and 110 tools in three folders;
  grouping by name prefix only. Fixed by this move (`src/<area>/`, manifests).
* **Makefile scaling**: four hand edits per module (CORE_NAMES, PROBE_NAMES, the 103-line
  `test:` recipe, a 2-line reference target), every object depending on every header.
  Fixed: wildcards, manifests, per-object dependency files.
* **Documentation as a journal**: a 197 KB handoff with 37 per-step entries plus a 668-line
  guide whose status section had to be edited by hand each step. Replaced by
  `docs/STATUS.md` (generated facts), `docs/ROADMAP.md` (plan), `AGENTS.md` (rules),
  with the old files kept as history.
* **Tool use**: Hopper (demo build) hangs regularly and is one function per query; the
  Ghidra runner was used only for `analyze_function`. REA's `list_procedures`,
  `batch_decompile`, `procedure_callers/callees`, snapshots and the seed file were not
  used. `docs/METHOD.md` fixes the workflow.
* **No visible output** after a day of work. M2 of the roadmap exists for that reason.

## Decisions taken (recorded in docs/decisions)

* ADR-0001: hybrid runtime (guest x86 + native HLE + overrides) replaces port-everything.
* ADR-0002: Ghidra via the owned REA runner is the analysis path; Hopper is not used.
* ADR-0003: repository layout, manifests, generated status; commits allowed on this repo.
