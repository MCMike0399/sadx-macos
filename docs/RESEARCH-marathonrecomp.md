# MarathonRecomp: static recompilation as a working port, and what it teaches sadx-macos

Status: research note. Read-only on this repository; the only file written is this one.
Date: 2026-11-16.
Author: research sub-agent.

This note answers one question: **what can a mature static-recompilation port teach a
function-by-function native port, without changing sadx-macos's destination?** It is
deliberately not a recommendation to recompile `sonic.exe`. ADR-0005, ADR-0006 and ADR-0007
rule that out, and section 3 explains why this project's product would be worse, not better,
if it copied MarathonRecomp's model.

## 1. What MarathonRecomp is and how it works

### 1.1 Product shape

Marathon Recompiled is an unofficial PC port of the Xbox 360 version of *Sonic the Hedgehog
(2006)*, shipped for Windows, Linux and macOS (`README.md:7-11`). It is a complete, released
port: an installer, the game application, original menus plus a custom ImGui options layer,
achievements, keyboard bindings by configuration file, audio, movies, and DLC. It contains no
game assets; the user supplies an Xbox 360 disc dump or installed files, and the installer
validates and copies them (`README.md` "How to Install", `MarathonRecomp/install/installer.cpp`).

The codebase is best understood as **three layers**:

1. **Generated game code** — C++ produced at build time by XenonRecomp from the original
   PowerPC executable. It is not in the repository and is not human-edited.
2. **A typed description of the original game's classes** — 510 headers under
   `MarathonRecomp/api` (the per-class headers are hand-maintained; the aggregate
   `api/Marathon.h` is generated by CMake), used by hand-written patches and by the host layer
   to read and write guest objects.
3. **A hand-written host platform** — Xbox kernel/XAM/XAudio shims, input, audio, the graphics
   device, the installer, configuration, menus, and ~6,000 lines of patches that hook specific
   recompiled functions.

That split is the central fact for this report: the "game codebase" a maintainer edits is
layers 2 and 3, not the game logic. The game logic is regenerated.

### 1.2 Static recompilation is a build step, not a checked-in source tree

`MarathonRecompLib/CMakeLists.txt` wires the recompiler into the build:

* It points XenonRecomp at `MarathonRecompLib/private/default.xex` and at
  `config/Marathon.toml.in`, and writes the generated sources to
  `${CMAKE_CURRENT_BINARY_DIR}/generated/ppc` (`MarathonRecompLib/CMakeLists.txt:20-56`).
* It expects exactly 146 output translation units, `ppc_recomp.0.cpp` … `ppc_recomp.145.cpp`,
  plus `ppc_config.h`, `ppc_context.h`, `ppc_func_mapping.cpp` and
  `ppc_recomp_shared.h` (`MarathonRecompLib/CMakeLists.txt:34-56`).
* It also runs `u8extract` on `shader.arc` / `shader_lt.arc`, then XenosRecomp to produce
  `shader_cache.cpp` (`MarathonRecompLib/CMakeLists.txt:64-100`).

The config is an explicit description of the binary, not a list of source files:

* `[main]` gives the XEX path, output directory, and jump-table file
  (`MarathonRecompLib/config/Marathon.toml.in:1-9`).
* Register save/restore helper addresses, `longjmp`/`setjmp`, and invalid-instruction ranges are
  declared by address (`Marathon.toml.in:11-93`).
* `functions = [...]` lists 58 explicit function boundaries where the analyser needed help.
  XenonRecomp's own README says the analyser derives the rest from `.pdata` and branch-link
  scanning, and that the explicit list is the workaround for functions with jump tables
  (`XenonRecomp/README.md`, "Function Boundary Analysis", "Explicit Function Boundaries").
* `switch_table.toml` contains 587 jump tables, mostly generated by XenonAnalyse, with a manual
  section at the top (`switch_table.toml:1-2`, "Generated by XenonAnalyse").
* `[[midasm_hook]]` entries (171) name a C++ function to call at a specific instruction, with a
  register list and optional return/jump behaviour (`Marathon.toml.in:95-130`;
  `XenonRecomp/README.md:223-236`).

Naming is mechanical. XenonRecomp names a function from the XEX symbol when one exists, and
`sub_<hex>` otherwise, then emits `PPC_FUNC_IMPL(__imp__<name>)` / `PPC_FUNC(<name>)`
(`XenonRecomp/recompiler.cpp:2551-2567`; the `PPC_FUNC` alias scheme is documented in
`XenonRecomp/README.md:71-83`). Hand-written patches then add the semantic name as a comment,
for example `// Sonicteam::Player::State::TailsContext::Update` above
`PPC_FUNC(sub_8221A7D8)` in `MarathonRecomp/patches/player_patches.cpp`.

The override mechanism is worth noting because it is cleaner than it looks:

```cpp
PPC_FUNC_IMPL(__imp__sub_8221A7D8);
PPC_FUNC(sub_8221A7D8)
{
    if (!Config::TailsGauge) { __imp__sub_8221A7D8(ctx, base); return; }
    ...
    __imp__sub_8221A7D8(ctx, base);
}
```

A replacement body can run before, after, or instead of the original, and the original remains
callable through `__imp__`. Mid-asm hooks provide the same at instruction granularity. This is
the recompiler analogue of sadx-macos's override table, but with no guest CPU and no Unicorn:
the recompiled function is ordinary native code.

### 1.3 The runtime still loads the original executable image

This is the most important architectural fact for sadx-macos.

The installer parses `game/default.xex`, copies the decrypted/decompressed image into
`decrypted/default.bin` with a small header (`MarathonRecomp/install/installer.cpp:570-600`;
header layout `installer.h:20-30`). At startup the app:

1. Finds the module: `Installer::checkGameInstall` prefers `decrypted/default.bin`, then
   `game/default.xex` (`installer.cpp:312-331`).
2. Maps the image into one flat guest address space: `LdrLoadModule` memcpys the image to
   `g_memory.Translate(header.base)` (`main.cpp:130-160`).
3. Reads the entry point from that header and runs it on a guest thread:
   `GuestThread::Start({ entry, 0, 0 })` (`main.cpp:339-353`), which calls
   `g_memory.FindFunction(params.function)(ctx.ppcContext, g_memory.base)`
   (`cpu/guest_thread.cpp:132-140`).

So the shipped product is **recompiled code plus the original image as its data segment**. The
image supplies globals, tables, strings, resources and layout; the generated code supplies the
instructions. The repository never contains the generated code, and the build fails without the
user's XEX (`docs/BUILDING.md` §2). This is exactly the model ADR-0005 rejects for sadx-macos:
executable independence and a build from checked-in source.

There is also a meaningful amount of kernel reimplementation: `kernel/imports.cpp` implements
Xbox kernel objects (events, threads, mutexes), `kernel/xam.cpp` content roots and saves,
`apu/audio.cpp`/`apu/xma_decoder.cpp` the audio driver, `kernel/io/file_system.cpp` file I/O. These
are the same *shape* as sadx-macos's `src/hle` Win32 layer, but they are part of the shipped
product rather than a reference tier.

### 1.4 The host boundary

The boundary between generated code and host code is small and explicit:

* `kernel/function.h` marshals PPC registers and stack arguments into C++ calls
  (`PPCContext`, `ArgTranslator`), including float registers.
* `api/Marathon.inl:24-38` defines `MARATHON_VIRTUAL_BASE` and
  `MARATHON_VIRTUAL_FUNCTION`, which call through the guest object's vtable by index.
  `GuestToHostFunction` / `HostToGuestFunction` call a guest address from host code and a host
  function from guest code respectively.
* `exports.cpp` exposes host functions the game calls, e.g. `Game_PlaySound`, so the original
  code can invoke a native implementation directly.
* `preload_executable.cpp` is a Windows-only working-set trick to lock the executable image in
  memory; on macOS it is a no-op (`preload_executable.h`).

The lesson for sadx-macos is not the mechanism (it has no guest registers in the product); it is
that the boundary is **narrow, typed, and named after the original object**. Addresses still
appear in patches and in `api` layout code, but the interfaces host code calls are typed and
carry the original object's identity rather than a bare integer.

### 1.5 The graphics translation layer

This is the most substantial hand-written subsystem and the most relevant to sadx-macos.

**The original device is reimplemented, not emulated.** `gpu/video.cpp:1601-1665` builds a
`GuestDevice`, a guest-memory-layout struct that matches the original device class, installs a
table of `SetRenderState` functions, and returns its guest address as the created device. Most
states point at the game's own setters, which are hooked by address; unimplemented states point
at a host stub (`gpu/video.cpp:1630-1665`). The game keeps calling the device API it was written
against.

**Calls are queued, not executed inline.** Device methods enqueue a typed command from
`gpu/render_command.h` onto `g_renderQueue`, a
`moodycamel::BlockingConcurrentQueue<RenderCommand>` (`gpu/render_command.h:213-219`;
`gpu/video.cpp:616`). A dedicated `HostThread g_renderThread` drains the queue and executes
against the host backend (`gpu/video.cpp:3994`). This decouples the guest thread's frame from
GPU submission and makes the command stream inspectable.

**The backend is an abstraction, not a console emulator.** `gpu/video.cpp:1214-1227` picks
D3D12, Vulkan or Metal through [plume](https://github.com/renderbag/plume). There is no
translation of Xbox GPU commands; the original game's *device-level* API is the contract.
Metal is a first-class backend (`MARATHON_RECOMP_METAL`), not a compatibility shim.

**Shaders are converted offline.** XenosRecomp converts the game's Xenos shaders into a
compressed DXIL/SPIR-V/AIR cache at build time (`MarathonRecompLib/CMakeLists.txt:64-100`;
cache layout in `MarathonRecompLib/shader/shader_cache.h`). At runtime a `GuestShader` is keyed
by a 64-bit hash and looked up in the cache (`gpu/guest_shader.cpp:18-100`). A handful
of hashes are replaced with native shaders for enhancements such as radial blur or movie
playback (`gpu/guest_shader.cpp:60-100`).

**Pipelines are sanitised, hashed, cached and precompiled.** `PipelineState`
(`gpu/pipeline.h:10-51`) holds every state that can affect the host pipeline.
`SanitizePipelineState` clears fields that are irrelevant for the current combination (for
example, blend factors when blending is off, depth state when depth is off), so equivalent
states collapse to one pipeline (`gpu/pipeline.cpp:29-100`). `GetPipelineStateHash` hashes the
sanitised struct with XXH3 (`gpu/pipeline.cpp:14-27`). `gpu/cache/pipeline_state_cache.h` is a
checked-in, 1,487-line list of known `PipelineState` values, and
`Video::StartPipelinePrecompilation` compiles them in the background starting at app
initialisation, overlapping the intro logos
(`gpu/pipeline_precompile.cpp:49-80,573-578`). A `LoadingPipelineCompilationEvent` waits for
the remainder at the end of loading (`gpu/pipeline_precompile.cpp:49-80`).

**Vertex declarations are content-hashed.** `CreateVertexDeclarationWithoutAddRef` hashes the
D3D vertex-element array and reuses the host input layout (`gpu/vertex_declaration.cpp:9-45`).
This is the same idea as the pipeline cache, one level lower.

**Textures are guest resources that own host textures.** `CreateTexture` allocates a
`GuestTexture` in guest memory and immediately creates the host texture and view
(`gpu/resources.cpp:20-100`; layout in `gpu/video.h:211-232`). `LockTextureRect` maps system
memory for the game to write; `UnlockTextureRect` enqueues an upload of exactly that region
(`gpu/resources.cpp:177-200,337-338`; the queued command is consumed in
`gpu/video.cpp:1662-1676`). Sampling reads the
already-uploaded `GuestTexture`; there is no per-draw decode and no per-frame re-upload.

That last point is the single clearest gap in sadx-macos's current renderer (section 4, packet
A).

### 1.6 Assets, install, and integrity

The installer is a small, complete virtual-file-system layer plus a transaction:

* `createFileSystemFromPath` accepts an ISO, an Xbox content container, or a directory and
  returns one `VirtualFileSystem` (`install/installer.cpp:43-60`;
  `install/iso_file_system.cpp`, `install/xcontent_file_system.cpp`,
  `install/directory_file_system.cpp`).
* `checkFile` compares size and XXH3-64 against a generated hash list and records progress
  (`installer.cpp:66-130`). The lists are generated by `tools/fshasher`
  (`tools/fshasher/fshasher.cpp`; `install/hashes/game.cpp:1` says "File automatically
  generated by fshasher").
* `copyFiles` writes into the target, records every created file and directory in a `Journal`,
  and `rollback` removes them on failure (`install/installer.cpp:555-640`;
  `installer.h:24-90`).
* `checkInstallIntegrity` is the same checks without writing, exposed as `--install-check`
  (`installer.cpp:369`; `main.cpp:235-285`).
* DLC is detected by its `download.arc`, and only directories with valid content are mounted
  (`main.cpp:110-125`).

This is a genuinely good design for ADR-0005's one-time importer: **the importer proves what it
read, records every path it created, can verify an existing install, and can undo a failed
install.**

### 1.7 Configuration, mods, and "profile"

There is no SADX-style profile system. The equivalent is:

* `config.toml`, described by 160 typed settings in `user/config_def.h`, declared through
  `CONFIG_DEFINE*` macros that work in both the declaration and definition translation units
  (`user/config.cpp:383-435`). Each setting carries a section, a default, a "requires restart"
  flag, optional enum labels, optional localised name/description, and optional
  `Callback`/`LockCallback`/`ApplyCallback` (`user/config.h:175-200`).
* `Config::Load`/`Save` read and write TOML by iterating one global definition list
  (`user/config.cpp:766-900`). Unknown keys and unknown enum values are silently ignored or
  defaulted (`config.cpp:457-491`) — a policy sadx-macos must not copy, because M6 requires
  unknown keys to fail explicitly.
* The in-game options menu iterates the same definitions, so a new setting appears in the UI
  without a second registration (`ui/options_menu.cpp`, `g_configDefinitions`).
* Mods are the Sonic '06 ecosystem, not SADX's: `cpkredir.ini` / `modsdb.ini`, HMM/UMM mods,
  include-directory overlays for `.ar` archives, and optional save redirection
  (`mod/mod_loader.cpp:1-150`). This is a path-overlay loader, not a code-patch profile like
  SADX Mod Loader.

The transferable idea is the **single typed definition list that drives both the file and the
UI, with validation hooks**. The transferable anti-pattern is silent defaulting.

### 1.8 Code organisation and readability conventions

`api/README.md` is explicit about how the 510 headers are written (`api/README.md:5-40`):

* `camelCase` locals, `PascalCase` types, `SNAKE_CASE` macros; `m_` members, `p` pointers,
  `sp` shared pointers, `r` references, `g_` globals.
* Members are public, even if the original had them private, because that is "more convenient
  in a modding API" (`api/README.md:26`).
* `enum class` is prohibited because the game predates it (`api/README.md:24`).
* Mapped classes carry `offsetof`/`sizeof` assertions; unknown members are named
  `m_Field<hex>`; unmapped ranges use `MARATHON_INSERT_PADDING`
  (`api/README.md:31-40`).
* Function definitions live in `.inl` files next to the header, not in the header.

A representative header is `api/Sonicteam/Actor.h`: a class deriving from the original
`SoX::Engine::Task`, two fields, and three `MARATHON_ASSERT_*` lines. `api/Marathon.inl` supplies
the padding/assert macros and the virtual-call helper.

This is a **modding SDK over a memory image**, and it is internally consistent. It is not a
game codebase in sadx-macos's sense: the class names are real, but the game logic is generated
and the functions are `sub_<hex>`. ADR-0006 and ADR-0007 exist precisely to avoid this shape.

### 1.9 Testing and verification

There is no automated game test suite in the public repository:

* The app's CMake has no `enable_testing`, `add_test`, doctest, GoogleTest or Catch2 target
  (checked `CMakeLists.txt`, `MarathonRecomp/CMakeLists.txt`,
  `MarathonRecompLib/CMakeLists.txt`, `tools/CMakeLists.txt`).
* CI builds every platform and preset and uploads artifacts, but runs no tests
  (`.github/workflows/validate.yml`).
* XenonRecomp has a `XenonTests` CMake project, but its `.cpp` sources are gitignored
  (`XenonTests/.gitignore` contains `*.cpp`), so the public clone cannot run it.
* The README's bug policy is human: a bug that does not occur on original hardware must be
  accompanied by footage from original Xbox 360 hardware (`README.md`, "Known Issues").

The tools that do exist are asset/debug aids, not behavioural judges: `fshasher` (hash
manifests), `bc_diff` (diff and patch BCn textures; `tools/bc_diff/bc_diff.cpp`), `u8extract`
(U8 archive extraction; `tools/u8extract/u8extract.cpp`), `x_decompress` (Xbox decompression),
`file_to_c` (embed resources). Verification is "run the game and compare by eye or with a
capture".

This is the clearest contrast with sadx-macos. This repository's oracles, mutants, holdouts,
override-equivalence corpora, journeys and judge manifest are a stronger correctness model than
anything in MarathonRecomp. Do not import their verification culture.

### 1.10 macOS support

macOS is a first-class build target, but the macOS-specific code is thin:

* SDL3 for windowing/events (`thirdparty/SDL`, `sdl_listener.cpp`), plume for Metal
  (`gpu/video.cpp:1214-1227`), and `os/macos/*` for locale, process paths, logger, media, user
  and version (`os/macos/`).
* `os::process::GetExecutableRoot` handles the `.app` bundle with CoreFoundation
  (`os/macos/process_macos.cpp:1-45`), so game data can live next to the bundle.
* CMake builds `MACOSX_BUNDLE` with an `Info.plist` and icon, and ad-hoc codesigns it in CI
  (`MarathonRecomp/CMakeLists.txt`; `validate.yml` macOS job).
* Deployment target is macOS 13.0 (`CMakePresets.json:147-166`), and CI builds arm64 only
  (`validate.yml` macOS matrix).

There is no Metal-specific game logic: the same game code and the same command stream run on
all three backends.

## 2. Techniques that could transfer to sadx-macos

Ratings: **adopt-now** = the gap exists today and the technique is directly usable; **adapt** =
the idea is right but the engine, formats or destination require a different implementation;
**not-applicable** = the difference is fundamental, or sadx-macos already has a better form.

| # | Technique | Evidence in the clone | Rating | sadx-macos target | Why / limits |
|---|---|---|---|---|---|
| 1 | A guest/asset resource owns its host object; upload only when the source changes | `gpu/resources.cpp:20-100` (`CreateTexture`), `:177-200,337-338` (`Lock`/`Unlock`); `gpu/video.h:211-232` (`GuestTexture` owns `textureHolder`); `gpu/video.cpp:1662-1676` (region upload) | **adopt-now** | `src/platform/mac/metal_guest_frame.mm:123-215`; `src/platform/mac/metal_device_frame.mm:247-297` | Today the guest frame decodes every texture into a fresh `graphics::Texture` per frame, and the shared device backend allocates and uploads a new `MTLTexture` per unique texture per frame (this affects the native path too, since `src/apps/sadx_native.mm:420-425` uses the same backend). Correctness is fine; the cost is not. A host-owned cache keyed by resource identity is a direct fix. |
| 2 | Sanitise pipeline state, hash it, cache it, and precompile the known set during loading | `gpu/pipeline.cpp:14-100`; `gpu/pipeline_precompile.cpp:49-80,573-578`; `gpu/cache/pipeline_state_cache.h` (1,487 lines) | **adapt** | `src/platform/mac/metal_device_frame.mm:185-225` | sadx's pipeline key is already narrow, so the first step is measurement, not a rewrite. The transferable parts are the sanitise-before-hash discipline, a `pipelines_created`/`cache_hits` counter, and prewarming from a generated list during the loading screen. Do not add a persistent cache until a journey shows a hitch. |
| 3 | Content-hash vertex declarations / input layouts | `gpu/vertex_declaration.cpp:9-45` | **not-applicable** | FVF decoding in `src/engine/graphics_frame.cpp` (`decode_vertices`) | Sadx decodes FVF vertices into its own `graphics::Vertex` per draw; it does not create host input-layout descriptors, so there is no descriptor to cache. The FVF field plan is recomputed per draw but is a few masks; measure before optimising. |
| 4 | A typed command queue between game code and the render thread | `gpu/render_command.h`; `gpu/video.cpp:616,3994` | **not-applicable** | `src/engine/graphics_frame.hpp`; `src/apps/sadx_native.mm:420-425` | Sadx already has an owned command list (`graphics::Frame`) consumed by one backend. Whether to move submission to a second thread is a separate performance decision, not a design import; the existing stream is the right seam. |
| 5 | Transactional importer: journal, rollback, per-file hashes, integrity mode | `install/installer.cpp:66-130,555-640`; `install/installer.h:24-90`; `installer.cpp:369` | **adapt** | `tools/import/native_assets.py`; `tools/import/file_select_display.py:57` (`atomic_json` only) | The importer writes dozens of outputs in sequence and has no pack-level transaction or verify mode. The pattern transfers almost unchanged; the formats and file lists do not. See packet B. |
| 6 | A generated hash manifest for every input file | `tools/fshasher/fshasher.cpp`; `install/hashes/game.cpp:1` | **adopt-now** | `tools/import/*.py` (per-module `SOURCE_SHA` constants) | Sadx already pins some sources by SHA-256, but not one manifest covering the whole pack. A single `pack.json` with source and output digests is cheap and makes the importer auditable. |
| 7 | A VFS over directory/container with explicit content roots | `install/{iso,xcontent,directory}_file_system.cpp`; `kernel/xam.h:1-30` | **adapt** | importer readers; reference-lane overlay in `src/hle/hle_process.cpp` | Useful when a user supplies a disc image or an install directory and when the reference app needs a stable mount point. Not needed for the native runtime, which reads the imported pack. |
| 8 | A first-run wizard as an explicit state machine with cancel and rollback | `ui/installer_wizard.cpp:1-110`; `install/installer.h:24-60` | **adapt** | no native first-run import flow today; `tools/import/native_assets.py` is a CLI | The product needs a one-time import path a normal player can use. The wizard's page/step structure, progress journal and cancel semantics transfer; the ImGui implementation does not. |
| 9 | One typed settings definition list drives the file, validation and the UI | `user/config.h:175-200`; `user/config_def.h` (160 settings); `user/config.cpp:383-435,766-900`; `ui/options_menu.cpp` | **adapt** (M6) | `src/enhancements/` (planned in `docs/ARCHITECTURE.md`); `docs/STYLE.md:191-223`; ROADMAP M6 | The shape (section, default, requires-restart, callback, localised label, enum values) is a good fit for `settings-roundtrip` and `enhancements-off-parity`. ## 3. What does NOT transfer, and why

### 3.1 The engine, the binary and the API are different at every level

| | MarathonRecomp | sadx-macos |
|---|---|---|
| Game | Sonic the Hedgehog (2006), Xbox 360 | Sonic Adventure DX (2004), Windows PC |
| CPU | PowerPC Xenon, 64-bit, big-endian | x86, 32-bit, little-endian, x87 |
| Graphics API | D3D9-shaped Xenos device + Xenos shaders | Direct3D 8 fixed-function + FVF |
| Assets | `.ar`/`.arl`, XEX, XMA, DDS/BCn | PVM, PRS, ADX, SET/CAM, `.exe`-embedded tables |
| Mods | CPKREDIR/UMM/HMM path overlays | SADX Mod Loader code patches + pinned profile |
| Build input | `default.xex` + shader archives | checked-in source + imported pack |
| Product runtime | generated code + original image | native code + imported assets |

Nothing at the instruction, asset or shader level transfers. What transfers is *engineering
discipline around resources, assets and configuration*, which is what section 2 lists.

### 3.2 The product still depends on the original executable image

This is not a detail; it is the destination difference. MarathonRecomp installs
`decrypted/default.bin` and maps it at startup (`installer.cpp:570-600`;
`main.cpp:130-160,339-353`). The generated code is not in the repository and is regenerated
from the user's XEX (`docs/BUILDING.md` §2). ADR-0005 requires the opposite: a build from
checked-in source, and a runtime that never opens `sonic.exe`. Copying their build or runtime
model would violate the project's central decision.

### 3.3 Generated `sub_` code is not readable source, and their API headers do not fix that

The 510 `api` headers are impressive, but they are a **typed memory map**: real class names,
public members, offset asserts, and little behaviour (inline helpers and typed layout access,
not the game's algorithms). The behaviour lives in generated
`ppc_recomp.*.cpp` files with `sub_<hex>` names. A developer can find `Actor::m_ActorID`, but
cannot read `Actor::Update` as code. That is precisely the failure mode ADR-0006 describes:
"static recompilers that keep `f_<hex>` names never became readable"
(`docs/decisions/ADR-0006-*.md`). Adopting the header style without the generated code would
give sadx-macos a second, redundant type system; adopting both would abandon ADR-0007.

### 3.4 Their verification model is weaker than this repository's

MarathonRecomp verifies by building on three platforms and by human comparison against
original hardware (`README.md`, "Known Issues"; `.github/workflows/validate.yml`). There is no
automated state, frame, audio or save test. That is a reasonable choice for a project whose
correctness is "the original instructions, recompiled", but it is the wrong choice for a
project whose correctness is "recovered semantics, judged by oracles". Sadx-macos's L0–L9 test
stack (`docs/TESTING.md`) is the reason it can claim fidelity at all. A research note that
recommended their testing approach would be recommending a regression.

### 3.5 Licence and contribution policy

MarathonRecomp is GPL-3.0 (`COPYING`); sadx-macos is MIT (`LICENSE`). Copying code would
relicense this project's source. Their `CONTRIBUTING.md` also bans AI-generated contributions
and says such proposals will likely be rejected; that is their policy for their repository, and this
report neither contributes to it nor copies from it. Study the design, write the code here.

### 3.6 Patch culture and config booleans in recompiled bodies

`patches/*.cpp` mixes behaviour, config gates, raw guest addresses, engine quirks and UI
changes in one function body, for example `patches/misc_patches.cpp:1-100`. It works because
the surrounding code is generated and address-shaped already. In sadx-macos the game tier must
read as a game; an `if (Config::X)` inside a recovered function is an enhancement decision and
belongs in the M6 hook registry, not in the faithful algorithm (`docs/STYLE.md:191-223`).
Their `bool AlwaysExitVehicles()` predicate style is the readable end of this spectrum, but it
is still a hook keyed by an instruction address. Sadx's `VanillaBehavior::should` is the
native equivalent and is already specified.

### 3.7 What the comparison validates

MarathonRecomp is evidence for three things sadx-macos already believes:

* Static recompilation produces a running port quickly, but it does not produce a game
  codebase; ADR-0005/0006/0007 are the right destination for a maintainable port.
* A real asset importer with hash checks, a journal and rollback is a product feature, not
  ceremony (their installer is one of their strongest subsystems).
* Resource ownership is where ports quietly lose performance. Their `GuestTexture` owning its
  host texture is the thing sadx-macos's current renderer is missing.

It is also evidence for one thing sadx-macos should not copy: a mature port can ship with no
automated behavioural tests, because its correctness is inherited from the binary. Sadx-macos's
correctness is not inherited; it is judged.

## 4. Top 3 highest-value follow-ups

Each packet is written to be durable (`packet/<name>` branch, `PACKET.md`, evidence under the
worktree's `reference/` or `build/`, per `docs/GOAL.md` §8). None changes the destination, the
fidelity policy or the judge. None copies GPL code.

### Packet A — `packet/texture-resource-cache`: own host textures and upload on change

**Problem (demonstrated, not speculative).** The current Metal path decodes and uploads every
texture used by every frame:

* `MetalGuestFrameRenderer::encode` creates a new `graphics::Frame` and a per-call
  `std::map<uint32_t, std::shared_ptr<graphics::Texture>>`, and calls `texture_image(...)` for
  each unique guest texture (`src/platform/mac/metal_guest_frame.mm:123-215`).
  `texture_image` decodes the base level and every mip level from guest memory on every call
  (`metal_guest_frame.mm:76-108`).
* `MetalDeviceFrameRenderer::encode` creates a per-call
  `std::map<const graphics::Texture *, id<MTLTexture>>` and `Impl::texture` allocates a new
  `MTLTexture` and `replaceRegion`s every level (`src/platform/mac/metal_device_frame.mm:247-297`).
* `MetalFrameStats` counts clears, draws and textured draws, but not textures uploaded or bytes
  (`src/platform/mac/metal_device_frame.hpp:10-13`), so no test notices the cost.

At the admitted CharacterSelect display (106 draws, 3,060 vertices, `docs/GOAL.md` §6.1) this is
tolerable. In a stage with hundreds of textures it is not, and the 63 FPS acceptance
(`docs/GOAL.md` §1.2 and §3.1 row P) makes it a correctness-of-performance issue.

**Scope (one packet, no visual change).**

1. **Product path.** Cache `id<MTLTexture>` per `graphics::Texture` identity in
   `MetalDeviceFrameRenderer`, with a generation counter on the texture so a replaced texture
   is re-uploaded. This is the bigger win: the native path re-uploads every asset texture every
   frame. Evict on renderer teardown or when the owning asset is released; do not grow without
   bound.
2. **Reference path.** Give the guest decode an identity: the guest object address plus a
   content version. The HLE currently throws that notification away —
   `IDirect3DTexture8::UnlockRect` is a no-op returning `D3D_OK`
   (`src/hle/hle_d3d8.cpp:121-124`) — so make that boundary bump a monotonic version on a side
   table keyed by the guest texture object. Do not hash pixels; the unlock is the notification
   you already have. Then cache the decoded `graphics::Texture` in `MetalGuestFrameRenderer` by
   object + version. Keep the existing `std::shared_ptr` ownership so frames can still refer to
   a texture safely.
3. Add `textures_created`, `textures_uploaded`, `texture_bytes_uploaded` and `cache_hits` to
   `MetalFrameStats`. These are the test surface.
4. Keep the guest/asset decode split: `metal_guest_frame` must not become dependent on the
   native asset pack, and `metal_device_frame` must stay guest-free.

**Acceptance.**

* Encoding the same unchanged frame twice performs **zero** `newTexture` and **zero**
  `replaceRegion` on the second encode (measured by the new stats).
* Changing one texel and bumping the version re-uploads once and the image checkpoint changes
  in exactly that region.
* R1–R4 reference journeys and the three native journeys keep their current image results;
  `make gate` is rc 0.
* A recorded CharacterSelect offscreen script shows the texture-upload counter flat after the
  first frame; repeat for Station Square when N4 has an offscreen script.

**Verification, using this repo's machinery.**

* New unit test `tests/unit/metal-texture-cache.mm` (or `.cpp` if it can be written against the
  `graphics::Texture` interface), registered with one `tests/unit/manifest.tsv` line. If it
  needs `X86Guest`, link `libsadx-guest.a` as `metal-sprite-composition-test` does; otherwise
  the generic `.mm` rule already links the platform archive.
* Manual mutation, the same discipline as `tools/gate/mutate.py`: force the cache to miss every
  frame, and the test must fail; force it to ignore the version counter, and the
  re-upload-after-change test must fail. Record both in `PACKET.md`.
* No oracle. This is platform code with no original guest function to compare; inventing an
  oracle here would be ceremony. The image checkpoints are the fidelity judge, and the counter
  assertions are the performance judge.
* If the decode is later moved into `engine/ninja_texture` (a recovered function), that move
  gets `tests/probes/native_<slug>_probe.cpp` + `tools/oracles/verify_original_<slug>.py` +
  `make oracle-<slug>` like any other owner; do not bundle that recovery into this packet.

**Non-goals.** No texture compression, no streaming, no sampler changes, no new Metal
features, no guest-ABI change.

### Packet B — `packet/import-transaction`: a transactional, verifiable asset importer

**Problem (demonstrated).** `tools/import/native_assets.py` runs 26 `import_*` calls in sequence
and writes directly into the output tree; only some outputs use `atomic_json`
(`tools/import/file_select_display.py:57-67`). Many use `Path.write_text` or `shutil.copyfile`
directly (`native_assets.py`, tail). A failure halfway leaves a mixed pack with no record of
what succeeded, and there is no mode that verifies an existing pack. The per-module
`SOURCE_SHA` constants check a few inputs; there is no pack-level manifest.

**Scope (one packet, no format changes).**

1. Add `tools/import/manifest.py` with a small `PackWriter`:
   * stages every output under a temporary directory inside the output's parent filesystem;
   * records `path`, `bytes`, `sha256`, and the source identity for every file;
   * writes a top-level `pack.json` (`version`, tool version, input source hashes, output
     digests, list of explicit boundaries such as voice 2047);
   * on success, installs the staged tree in two phases: move the previous pack to a backup,
     move the staged pack into place, delete the backup; on failure, restore the backup;
   * on any exception before the swap, removes the staging directory and leaves the previous
     pack untouched.
2. Add `--verify` to `native_assets.py`: read `pack.json`, re-hash every file, report the first
   mismatch with its path and expected/actual digest, exit non-zero. This is the analogue of
   `Installer::checkInstallIntegrity` (`install/installer.cpp:369`).
3. Migrate the existing import functions to take a `PackWriter` (or a thin `write(path, bytes)`
   callback) so no step writes the final tree directly. This is mechanical; do not change the
   formats or the selected asset lists.
4. Keep `pack.json` out of the game runtime until a reader needs it; it is an importer and
   verification artifact, not a new runtime dependency.

**Acceptance.**

* A fault injected at each of three points (after the first asset, halfway, before the manifest
  write) leaves the output tree exactly as it was before the run. No orphan files, no partial
  `pack.json`.
* A single flipped byte in a source file fails the import with `path`, expected and actual
  SHA-256; a single flipped byte in an output file fails `--verify`.
* A good pack imports twice in a row and the second `pack.json` is byte-identical (modulo a
  documented timestamp field, if one is added; prefer none).
* The existing native journeys run from the newly imported pack with the same image and state
  results; `make gate` is rc 0; `tools/gate/check_repo_hygiene.py` still finds no game assets
  committed.

**Verification, using this repo's machinery.**

* `tests/python/test_import_transaction.py`, discovered by `make test`'s
  `unittest discover -s tests/python` (`Makefile:345`); `make gate` runs `test` as a
  prerequisite. Use `unittest.mock.patch` to raise after the Nth write; assert the tree hash
  before and after is identical.
* `tests/python/test_import_manifest.py`: good pack verifies; flipped output fails; missing
  file fails; unknown manifest version fails explicitly.
* `tests/python/test_import_*.py` already exist per asset format; they keep their unit-level
  role. This packet tests the transaction and the manifest, not the codecs.
* Full gate (`make -j10 gate`), recorded with `tools/gate/record_gate.py` only if this packet
  is integrated as a step; the last recorded gate and `docs/STATUS.md` remain the authority.
* Not an oracle. If a future importer step decodes a value from `sonic.exe`, that decode keeps
  its existing Python test and source hash; the manifest does not replace it.

**Non-goals.** No new asset formats, no stage-geometry importer, no UI, no change to the
existing selected-asset lists, no change to `game/` or `reference/` inputs.

### Packet C — `packet/guest-texture-layout`: typed layouts for the renderer's guest decode

**Problem (demonstrated).** `metal_guest_frame.mm` reads the original texture object through
raw offsets with no type and no assert:

```cpp
const auto table = memory.u32(object + 40);
const auto surface = table ? memory.u32(*table + 4 * level) : std::nullopt;
...
const auto width = memory.u32(*surface + 8), height = memory.u32(*surface + 12);
const auto format = memory.u32(*surface + 16), pitch = memory.u32(*surface + 20),
           bits = memory.u32(*surface + 24);
...
const auto levels = memory.u32(object + 36);
```

(`src/platform/mac/metal_guest_frame.mm:7-40,76-100`). The offsets match the assets tested so
far, but a wrong offset is invisible: the code compiles, the image checkpoint may still pass on
a different asset, and a field swap produces a plausible-looking texture. This is the exact
failure mode `docs/GOAL.md` §2 records ("correlated mistakes slip past local oracles"). It
matters more than a normal readability nit because this decoder is part of the judge: a wrong
field here can certify a wrong native frame. The packet is judge correctness first, readability
second.

**Scope (one packet, one class family).**

1. Add `src/platform/mac/guest_texture_layout.hpp` (or `src/guest/guest_texture_layout.hpp` if
   it is shared with the reference adapters) with:
   * `struct GuestTextureObject` and `struct GuestSurface` using named fields at the offsets
     currently hard-coded;
   * `static_assert(offsetof(...) == 0x28)` etc. for every field, and a `sizeof` assert where
     the size is known;
   * a short comment above each assert naming the evidence (symbol database / mod loader
     header / Ghidra layout), not a bare hex.
2. Replace the raw reads in `metal_guest_frame.mm` with the named struct, keeping the same
   read order and the same error strings. The decode helpers are currently static in an
   anonymous namespace (`metal_guest_frame.mm:5-108`), so move them behind a small internal
   header (for example `metal_guest_texture.hpp`) that the unit test can call; keep it out of
   the public platform interface.
3. Do not add accessors that hide the layout; the point is a readable, checked view of guest
   memory, not a new abstraction layer.
4. If the same fields are read in more than one place, put the struct in one header and borrow
   it; do not duplicate offsets.

**Acceptance.**

* `metal_guest_frame.mm` contains no arithmetic on the texture/surface object other than
  `object` plus a named field (or an array index into a named table).
* Compile-time asserts cover every field currently read by the decode.
* The decode produces the same width/height/format/pitch/bits for the existing assets; all
  image checkpoints are unchanged.

**Verification, using this repo's machinery.**

* New unit test `tests/unit/metal-guest-texture-layout.cpp` with a synthetic guest memory:
  write a distinct, valid value at every field offset, then assert the decode reports the
  width, height, format, pitch, bits and level count from the matching field. Swapping two
  offsets in the struct must make the test fail. This is the local version of the GOAL §2
  lesson "check owner mappings with distinct non-zero values". If the test needs `X86Guest`,
  add a specific Makefile rule linking `libsadx-guest.a`, as `metal-sprite-composition-test`
  does.
* Manual mutation, recorded in `PACKET.md`: swap `width`/`height`, then `pitch`/`bits`; the
  sentinel test must fail both times. (The compile-time asserts will not catch a swap of two
  same-sized fields; the sentinel test is the judge.)
* Image checkpoints for the existing texture-bearing journeys; `make gate` rc 0.
* No oracle. These are platform reads of guest memory, not a recovered guest function. If the
  same layout is used by a recovered function, that function's existing oracle already covers
  it; the layout header must not weaken it.

**Non-goals.** No change to the offsets, no new texture formats, no move of decode into the
assets layer, no `metal_guest_frame` → `engine` dependency. This packet is deliberately small:
it makes the current code auditable before the stage renderer grows.

## 5. Bottom line

MarathonRecomp is a strong example of a **different** way to reach a running port: recompile the
instructions, reimplement the platform, and patch the differences. It is fast to a playable
build and it produces a real product, but its game logic is generated `sub_` code, its build and
runtime depend on the original executable image, and its correctness is inherited rather than
judged. None of that fits ADR-0005/0006/0007, and section 3 says why.

What does fit is narrower and useful: **resources should own their host objects and update on
change** (packet A), **an importer should be a transaction with a manifest and a verify mode**
(packet B), and **guest layouts should be typed and asserted, not raw offsets** (packet C).
Those three are in the current N3b→N5 path, they need no change to the destination, and each has
a concrete judge in this repository's existing unit/gate/journey machinery.

The rest of their design — typed settings, per-class hooks, pipeline prewarming, a first-run
wizard — is worth revisiting when the route reaches M6 or when a measurement shows a hitch.
The pipeline cache is explicitly *measure first*: sadx's fixed-function key is already small,
and a cache added without a demonstrated stall would be ceremony.
